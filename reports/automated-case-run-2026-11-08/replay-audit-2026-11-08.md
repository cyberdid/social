## Що встановлено, а що ні

- Перевірка підтверджує цілісність байтів відносно збережених маніфестів, а не істинність claims або повноту доказів.
- Поточний повторний запуск завершився як bounded run. `source_lineage` лишився `blocked`; `claim_retrieval` — `blocked`. Event reconstruction, conflict analysis, information dynamics, uncertainty scenarios, report generation та структурна evaluation позначені runner-ом як `complete`.
- `verification_results.jsonl` порожній. Retrieval output не є підтвердженням тверджень; у цьому повторному запуску немає прийнятих Evidence Assessments чи `VerificationResult`.
- Основний запуск не встановлює незалежність джерел, фізичну хронологію, причинність, повноту джерельного покриття або семантичну точність звіту.
- Історичні та повторні JSON можуть відрізнятися через зміну часу виконання чи серіалізації; хешова різниця не пояснює причину без окремого diff-аналізу полів.

## Відтворюваність і межі provenance

Поточний повторний запуск використовував Python 3.12.3, commit `bb8e019c69597448428bfd0fb2c313c66f4cea31` та той самий набір із восьми входів, що й історичний manifest. Команда з placeholders і хеші кожного входу/виходу зафіксовані у JSON receipt. Точні абсолютні шляхи до приватних входів навмисно не включені.

Робоче дерево було змінене. Знімок хешів коду у receipt зроблено після повторного запуску; він **не** відновлює точний dirty diff на момент запуску. Lock-файл залежностей відсутній. Тому це точний облік входів і виходів двох запусків, але не повна герметична реконструкція середовища запуску.
