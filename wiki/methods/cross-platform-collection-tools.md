# Збір публічних дописів X, Facebook, Instagram, Threads та відеоплатформ

Дата перевірки: **5 листопада 2026 року**. Це огляд доступу й інструментів та цільова проба одного наданого користувачем TikTok, а не повний корпус інциденту. Початковий реєстр із часом звернень, HTTP-статусами, хешами джерел, версіями та результатами проб: [`raw/research/collection-tool-sources.json`](../../raw/research/collection-tool-sources.json). Подальший TikTok snapshot описано окремою [квитанцією](../../raw/research/tiktok-fire-20261105T105600Z-snapshot-receipt.json).

**Практичне рішення:** `public-clis/twitter-cli` придатний для швидкого перегляду X; для дослідницького збирача варто пілотувати `twscrape` зі збереженням сирих відповідей або офіційний X API. Для Instagram уже вдалося анонімно прочитати один публічний допис через Instaloader. Для Facebook немає перевіреного тут універсального анонімного збирача: конкретні URL, дозволений Pages API та Meta Content Library вирішують різні частини задачі. Threads має офіційний пошук публічних дописів, який потребує погодженого дозволу.

## Що означає «перевірено»

- **D — документація:** прочитано актуальне первинне джерело; запит до платформи з авторизацією не виконувався.
- **S — код:** перевірено реалізацію за конкретним commit.
- **L — локально:** інсталяція, версія, довідка або тести з fixtures/mocks.
- **P — публічна проба:** виконано невеликий запит без входу в акаунт. Успіх однієї проби не доводить повноту або стабільність збору.

Усі інсталяції зроблено в тимчасовому virtualenv `/tmp/social-collection-tools-venv`. Користувацькі cookies, ключі, сесії та браузерні профілі не читалися; входів і публікацій не було. Початкові smoke tests не завантажували медіа; пізніше за конкретним URL користувача збережено публічне TikTok-відео. Частина Meta-документації повертала HTTP 429 інструменту вебперегляду, але була успішно прочитана звичайним HTTPS-запитом без авторизації; ці звернення є в реєстрі.

## Розбір саме public-clis/twitter-cli

Перевірений commit: [`7c634e0d396b1e7af9f63315b414925fe4f29ae7`](https://github.com/public-clis/twitter-cli/commit/7c634e0d396b1e7af9f63315b414925fe4f29ae7), датований 7 травня 2026; package **0.8.6**, Python ≥3.10, Apache-2.0, classifier Alpha. README і package metadata ще містять старі адреси `jackwener/twitter-cli`; це враховано під час ідентифікації пакета. Перевірено код саме в запитаному `public-clis` repository. [pyproject.toml](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/pyproject.toml).

Це клієнт внутрішніх web GraphQL endpoints X. `SearchTimeline` викликається через HTTP POST, хоча операція читає пошукові результати. Авторизація: `TWITTER_AUTH_TOKEN` і `TWITTER_CT0`, інакше код пробує витягувати cookies з браузерів; підтримує передачу всіх X-cookies. «Без API keys» не означає «без X-акаунта». Для дослідження слід мати явно налаштовану окрему сесію за правилами проєкту в `~/.config/social/`, а не покладатися на автоматичний пошук браузерних профілів. [auth.py](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/auth.py), [client.py](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/client.py).

Практичні можливості й пастки реалізації:

1. **Пошук.** Є keyword/exact phrase через query, `--from`, `--to`, `--lang`, `--since`, `--until`, медіафільтри, `Latest/Top/Photos/Videos`. Для вибірки не вмикати `--filter` або пороги engagement: вони цілеспрямовано відсіюють слабко поширені дописи. `Top` — початкове значення; для часової вибірки треба явно `--type Latest`.
2. **Ліміти й пагінація.** `_fetch_timeline` переходить за cursor і дедуплікує за tweet ID, але обмежує запит `maxCount`: default 200, абсолютний cap 500. `--max 10000` не означає отримати 10 тисяч. На `twitter search` немає `--cursor`; search також не повертає resumable pagination metadata. Cursor, описаний у README, реалізований для окремих timeline/list команд. Точні невеликі вікна запитів і явний журнал зупинок потрібні навіть для пілоту. [CLI](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/cli.py), [pagination implementation](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/client.py).
3. **Метрики.** Експорт містить likes, retweets, replies, quotes, views, bookmarks. Відсутнє значення `views` парсер замінює на **0**. Тому нуль із normalized output не доводить, що допис ніхто не переглянув. Для коректної missingness потрібна сира відповідь або окреме поле доступності метрики. Це лічильник на момент збору, а не унікальні люди чи перегляди на час події.
4. **Репости.** Для retweet парсер бере **ID, час, текст, автора й метрики оригіналу**, залишаючи `is_retweet` і `retweeted_by`. Окремі ID/time retweet-події губляться; дедуплікація за original ID може згорнути різні репости. Таким експортом не слід вимірювати лаги репостів чи кількість подій поширення. Це встановлено за кодом, не перевіркою live-акаунта. [parser.py](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/parser.py).
5. **Медіа.** Повертає photo URLs та MP4 URL найбільшого bitrate з наявних variants, тип/розміри; не архівує самі файли. URL може протермінуватися. Для збереження публічного відео потрібна окрема операція з фіксацією URL, часу й хешу файлу. [Media parser](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/parser.py).
6. **JSON не завжди однаковий.** `--json` stdout має `ok/schema_version/data`, а `--output` записує serialized tweet array. Non-TTY stdout за замовчуванням YAML. Не вважати stdout JSON без явного прапорця; зберігати версію схеми. Парсер нормалізує дані, а не зберігає повний GraphQL response. [SCHEMA](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/SCHEMA.md), [serialization](https://github.com/public-clis/twitter-cli/blob/7c634e0d396b1e7af9f63315b414925fe4f29ae7/twitter_cli/serialization.py).

Пакет також має команди запису; дослідницький runner має викликати лише дозволені read-команди. Bookmarks, власні likes, приватні/платні матеріали не входять у public-only корпус цього проєкту. Головна причина не брати цей CLI як основний збирач — описані обмеження відтворюваності та подій, а не сама відсутність офіційного API key.

### Що дає twscrape натомість

Перевірений commit [`e87459615053aea171178ba19608e63718a85788`](https://github.com/vladkens/twscrape/commit/e87459615053aea171178ba19608e63718a85788), package **0.20.1**, MIT. Дата commit — 30 жовтня 2026; GitHub metadata показував push 31 жовтня. Це ознака свіжішої активності, але не доказ працездатності запитів.

У коді `search_raw` використовує `Latest`; є streaming async iteration, `--raw`, parsed `date/id`, вкладені `retweetedTweet/quotedTweet`, nullable `viewCount`, conversation/reply references. Ця форма краще підходить для перевірки лагів і збереження походження. Потрібно окремо перевірити, чи X реально віддає retweet-події в обраному endpoint; сам `retweetCount` їх не замінює. [Models](https://github.com/vladkens/twscrape/blob/e87459615053aea171178ba19608e63718a85788/twscrape/models.py).

Для першого пілоту достатньо **однієї власної явно наданої сесії**. Функції ротації акаунтів/проксі не є умовою методології; куплені акаунти не пропонуються. Session DB слід розташувати поза репозиторієм і захистити правами, як вимагає `CLAUDE.md`. Наявність internal API означає ризик зміни схеми/endpoint і непередбачуваних порожніх результатів.

## Особливості Meta, які впливають на план

**Meta Content Library не є відкритим CLI для будь-якої людини.** Поточні вимоги — affiliation із qualified academic або not-for-profit research institution. Заявки подають через **Meta Research Tools Manager**; незалежний review проводить **CASD**, а не старий ICPSR intake. Документація описує 2–3 тижні review і ще 2–3 тижні Meta processing; це орієнтир, не обіцянка. Meta SRE безкоштовний. SOMAR VDE — інший варіант: з 2026 року заявлено $1 000 onboarding та $371/місяць; ці ціни не слід переносити на SRE. [Meta get access](https://developers.facebook.com/docs/content-library-and-api/get-access), [SOMAR 2026](https://www.icpsr.umich.edu/sites/somar/somar-newsletter-archive/somar-newsletter-spring-2026).

**UI-покриття ширше за те, що можна завантажити.** Для Facebook UI включає public Pages/groups/events і public verified profiles або profiles від 100 followers; downloadable subset має вищі пороги. Для Instagram — business/creator accounts та public personal accounts від 100 followers або verified; downloads також мають вищі пороги. Threads UI включає public profiles від 100 followers, але download цього dataset недоступний. Це виключає трактування результатів як усієї платформи. [Поточний scope](https://developers.facebook.com/docs/content-library-and-api/content-library).

**API raw data не можна просто скласти у `raw/`.** Meta прямо забороняє downloading API data поза SRE/approved cleanroom. Відтворюваність такого аналізу забезпечують дозволені код, параметри, версії та reviewed outputs. Для UI downloadable subset перевіряти окремі умови; обов'язки видалення мають перевагу над звичкою зберігати raw незмінним. Не під'єднувати цей канал даних до поточного immutable raw pipeline автоматично. [API overview](https://developers.facebook.com/docs/content-library-and-api/content-library-api/overview), [SOMAR](https://www.icpsr.umich.edu/sites/somar/meta-content-library).

**Instagram hashtag API погано придатний для минулої події.** `recent_media` бачить лише останні 24 години й не повертає username; пошук конкретної події через два-три дні не відновить повний hashtag-корпус. Business Discovery вирішує іншу задачу — пости відомих professional accounts. Для незалежного початкового дослідження практичніший список public URL/профілів і обмежений пілот Instaloader. [Recent Media](https://developers.facebook.com/docs/instagram-api/reference/ig-hashtag/recent-media).

**Threads уже має офіційний public keyword search.** Не варто повторювати старе твердження «API лише для власних постів» без уточнення permissions. Для дослідження: `RECENT`, явні `since/until`, журнал запитів/порожніх відповідей; авторизація й App Review залишаються реальною передумовою. Часовий фільтр у документації не гарантує повного архіву. [Офіційна документація](https://developers.facebook.com/docs/threads/keyword-search/).

## Рекомендований план придбання даних для Social

1. **Спочатку зафіксувати корпус.** Окремо keyword discovery, seed-author timelines і перевірка вже відомих URL. Записати UTC-інтервал, початкові українські/російські варіанти ключів, правопис/транслітерацію, переліки публічних організацій/редакцій. Не ставити language filter відразу: змішані тексти й помилки визначення мови втратять релевантні дописи.
2. **X: короткий acquisition pilot.** Якщо є одна власна дозволена сесія, `twscrape` — кандидат на основний collector, `twitter-cli` — допоміжний огляд. Взяти невелике вікно й 2–3 known public posts; перевірити ID/date, retweet event проти original, порожні сторінки, повтори та припинення пагінації. Якщо потрібна документована історична повнота й є бюджет — пілот official API, порівняння ID coverage з web route; оплату/токени налаштовує користувач окремо. Поточна офіційна ціна Post read — $0.005/resource; перед реальним запуском перевірити console та встановити spending limit. [Pricing](https://docs.x.com/x-api/getting-started/pricing).
3. **Instagram: відомі URL/автори.** Публічний Instaloader pilot уже має позитивну пробу. Наступний крок — невеликий набір релевантних профілів і URL, timezone-normalized metadata та date cutoff. Не називати це глобальним пошуком Instagram. Якщо є погоджений official professional API, додати його як незалежний канал для тих акаунтів, які він покриває.
4. **Facebook: URL inventory + доступний дозволений шлях.** Спочатку зібрати permalink-и з первинних звітів, вебпошуку й публічних сторінок; архівувати видимі публічні матеріали по URL зі статусом retrieval. Для відомих Pages перевірити Pages API permissions. Для заяв типу «361 однаковий допис» потрібен первинний список ID/URL або відтворюваний пошук MCL; браузерна видача та media downloader не доводять цю кількість. Facebook-scraper — лише окремий обмежений test candidate, доки нема підтвердження live.
5. **Threads: official search pilot після доступу.** Запитати потрібний permission; почати з відомих public posts і контрольних keywords. Поки доступу немає, збирати знайдені permalink-и та датовані публічні свідчення; не підміняти відсутність API результатом «0 постів».
6. **Відео: discovery окремо від архівації.** YouTube API — пошук відео/стрімів і metadata; `yt-dlp` — повторна перевірка конкретного URL та збереження потрібного публічного медіа після успішного simulate. TikTok Research API розглядати лише після підтвердження eligibility; для початкового corpus — known public URLs і явно неповний discovery log. TikTok FAQ попереджає про до 48 годин індексації та до 10 днів оновлення counters: це заважає аналізу останніх годин. [FAQ](https://developers.tiktok.com/docs/en/research-api-faq).
7. **Вести журнал доступності.** Для кожного запиту: platform, method/endpoint, query/window, cursor in/out, requested/returned count, UTC retrieval time, tool version/commit, HTTP/error, stop reason і дозволений raw hash. Порожню відповідь, denied, rate limit та «не шукали» розділяти. Для кожного запису: platform post ID/URL, original UTC time, observed time, source response, reply/quote/repost relations, nullable counters. Тексти приводити до спільної схеми лише в processed.
8. **Оцінити покриття до висновків.** Перевірити known-item recall; повторити невелику підвибірку другим каналом; порівнювати IDs, а не тільки кількість. Це перевірка на контрольному наборі, не оцінка recall всієї платформи. Зупинка за cap/порожньою сторінкою — не доказ вичерпання всіх результатів. «Найраніший знайдений допис» завжди обмежений доступною вибіркою.

## Цільовий TikTok: фактичний доступ без дослідницького акаунта

Наданий користувачем shortlink `https://vt.tiktok.com/ZSpYXw2Gx` розкрився в [публічне відео `7704443960013376789`](https://www.tiktok.com/@anastasiyapalivoda/video/7704443960013376789). `yt-dlp --ignore-config --skip-download --dump-single-json` успішно повернув metadata без user cookies/login. Початковий звичайний HTML-запит отримав HTTP 200 із challenge-сторінкою; отже сам статус 200 ще не означає прочитання допису.

У metadata підпис складається лише з hashtag-ів, зокрема `#софіївськаборщагівка`. Твердження про приховування слідів знайдено **в коментарях**, а не в підписі. Платформний timestamp: **2026-11-04 22:17:34 UTC**; зазначена тривалість — 10 секунд. На першому знімку counters: views 767 800, likes 17 300, comments 796, reposts 8 363. Це лічильники на момент читання, не оцінка унікальної аудиторії чи показники на час публікації. Первинна metadata-відповідь збережена локально; [video receipt](../../raw/research/tiktok-fire-20261105T105900Z-video-receipt.json) фіксує завантажений MP4 та SHA-256. Назва hashtag сама по собі не є незалежною геолокацією пожежі.

Встановлений yt-dlp не має TikTok extractor для текстів коментарів. Окремий анонімний HTTP-запит через `curl_cffi` до `https://www.tiktok.com/api/comment/list/` із `aid=1988`, `aweme_id`, `count=50`, `cursor=0` повернув JSON зі `status_code=0`. Без `aid` інший запит повернув `status_code=5`, хоча HTTP також був 200. Для replies використано `/api/comment/list/reply/` з `item_id` відео, `comment_id` батьківського коментаря й cursor. Це внутрішні web endpoints; універсальна чи майбутня доступність не гарантується. Аналогічні endpoints задокументовані реалізацією [TikTokApi video.comments](https://github.com/davidteather/TikTok-Api/blob/main/TikTokApi/api/video.py) і [comment.replies](https://github.com/davidteather/TikTok-Api/blob/main/TikTokApi/api/comment.py); сам SDK тут не інстальовано і не тестовано.

**Отриманий snapshot:** 345 distinct top-level comments і 538 distinct replies, разом **883 ID**. Top-level pagination та всі 56 threads із заявленими replies завершилися `has_more=false`. Зроблено 53 нові запити з паузою 0.75 с та імпортовано 14 раніше збережених відповідей. В усіх повернутих replies поле `reply_id` відповідало запитаному батьківському коментарю.

**Це не доведена повнота.** Під час обходу total змінювався 796 → 798; сума advertised reply counts становила 493, тоді як distinct replies повернулося 538. У 9 threads counts не збіглися, зокрема перший коментар про сліди мав advertised 63 replies, endpoint повернув 94. Імовірні відмінності видимості/фільтрації/кешу та динаміка не розділені; не приписуємо невідповідність одній причині. Не ділимо кількість отриманих записів на displayed comment_count і не називаємо це відсотком охоплення коментарів. Видалені, недоступні й відфільтровані тексти таким знімком не відновлюються. Ранжування top-level comments не є часовим порядком.

У першій сторінці є і короткі звинувачення «замітають сліди катування людей???», «Замітають сліди катівні…», і виправлення, що Петропавлівська та Софіївська Борщагівка — різні населені пункти. Це перевіряє наявність обох типів реакцій у конкретному коментарному просторі; їхня частка, істинність геолокації та координація потребують окремого аналізу.

Відтворюваний [collector](../../src/tiktok_public_collect.py) створює новий snapshot, зупиняє нові запити після HTTP/platform error, не імпортує браузерні cookies й не пише headers/credentials у квитанції. Normalized JSONL містить `platform`, `video_id`, `video_url`, `comment_id`, `parent_id`, `text`, `created_at_utc`, `likes`, `reply_count`, `fetched_at_utc`, `pinned`; імена й профілі авторів не включені. Прямий comment permalink не вигадується: URL відео і comment ID збережені окремо.

```bash
# Після встановлення curl_cffi у вибране isolated environment:
python src/tiktok_public_collect.py \
  --video-id 7704443960013376789 \
  --video-url 'https://www.tiktok.com/@anastasiyapalivoda/video/7704443960013376789' \
  --output data/raw/tiktok/NEW_SNAPSHOT \
  --delay 0.75 --max-requests 120
```

Поточні source bodies і full manifest: `data/raw/tiktok/20261105T105600Z-fire-7704443960013376789/`. Канонічний normalized output: `data/processed/tiktok/20261105T105600Z-fire-7704443960013376789/comments.normalized.jsonl`. Квитанція для wiki/git: [snapshot receipt](../../raw/research/tiktok-fire-20261105T105600Z-snapshot-receipt.json). Початкові diagnostic raw bodies не публікуються разом із квитанціями. Чотири offline-тести перевіряють припинення після помилки, duplicates/exhaustion, відсутній cursor і відокремлення author data.

Публічний MP4 також завантажено через yt-dlp; він сам виконав native Python JS challenge handling і використав тимчасовий анонімний challenge cookie. Cookies користувача, акаунт, CAPTCHA чи зміни налаштувань браузерної безпеки не використовувалися. Перевірку відповідності локальному Telegram-export та встановлення місця пожежі цей інструментальний тест не замінює.

| Auto Archiver / yt-dlp як достатній збір платформ | Auto Archiver приймає список URL і оркеструє архівацію; це не глобальний пошуковий індекс. Працездатність extractor треба перевіряти для конкретного типу URL. Наш yt-dlp TikTok metadata/video test успішний; тексти comments отримано окремим collector. [Auto Archiver](https://github.com/bellingcat/auto-archiver) |
| Публічний контент загалом не порушує ToS; research послаблює вимоги безпеки GDPR | Такі загальні правові запевнення не переносимо в методику. Публічність не є універсальною правовою підставою обробки/дозволом умов сервісу. GDPR Art. 89 прямо вимагає safeguards і technical/organisational measures, зокрема data minimisation; це не загальне послаблення безпеки. [GDPR Art. 5, 6, 89](https://eur-lex.europa.eu/eli/reg/2016/679) |
| DSA як швидкий доступ для цього дослідження | Це окремий регуляторний шлях із eligibility, заявкою й DSC-процесом, а не спосіб негайно отримати доступ наявним особистим developer account. Не змішуємо його з public web read та стандартними platform research programs. [ЄК: data-access mechanism](https://digital-strategy.ec.europa.eu/en/library/delegated-act-data-access-under-digital-services-act-dsa) |
